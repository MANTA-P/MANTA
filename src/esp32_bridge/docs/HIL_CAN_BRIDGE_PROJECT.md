# BlueROV HIL CAN 브리지 및 버스 부하 실험

## 1. 문서 목적

이 문서는 MANTA 프로젝트에서 담당하는 **BlueROV 제어 로직의 HIL 전환**,
**UART-CAN 통신 경로 구성**, **CAN 버스 부하와 우선순위 실험**의 범위를
정리한다.

현재 구현된 기능과 앞으로 구현할 기능을 구분하고, 하드웨어 구성부터 데이터
흐름, 소프트웨어 역할, 시험 방법과 완료 조건까지 한곳에 기록한다.

## 2. 프로젝트 배경과 최종 목표

현재 시스템은 Gazebo와 SITL 안에서 BlueROV 및 위협 어뢰의 물리 동작과
제어를 시험한다. 최종 목표는 시뮬레이션의 물리 모델은 그대로 유지하면서
BlueROV의 회피·제어 로직을 실제 임베디드 보드에서 실행하는
Controller-HIL 구조로 전환하는 것이다.

- Gazebo/SITL은 BlueROV와 어뢰의 물리 모델 및 센서·상태 데이터를 생성한다.
- 어뢰 관련 시뮬레이션과 제어는 SITL에 유지한다.
- BlueROV 회피, 경로 추종 및 추진기 제어 계산은 ESP32 보드로 옮긴다.
- SITL과 제어 보드는 UART 및 CAN을 통해 상태와 제어 출력을 왕복한다.
- 동일한 CAN 버스에 가상 소나 덤프 트래픽을 추가하여 통신 부하와 우선순위
  영향을 관찰한다.

최종 데이터 흐름은 다음과 같다.

```text
Gazebo/SITL
  │
  │ BlueROV 상태, 센서, 목표, 어뢰 상태
  ▼ UART
ESP32 A: UART-CAN 게이트웨이
  │
  ▼ CAN
ESP32 B: BlueROV 회피 및 제어 로직
  │
  │ 6개 추진기 출력
  ▼ CAN
ESP32 A
  │
  ▼ UART
Gazebo/SITL의 BlueROV 추진기 입력
```

## 3. 담당 범위

이 파트에서 담당하는 작업은 다음과 같다.

1. PC와 ESP32 사이의 UART 통신 구현
2. ESP32 A의 UART-CAN 양방향 게이트웨이 구현
3. ESP32 B에 BlueROV 회피·제어 로직 이식
4. SITL 데이터와 CAN 프레임 사이의 직렬화 규격 설계
5. ESP32 B의 6개 추진기 출력을 SITL로 반환
6. Teensy 4.1 기반 가상 소나 부하 생성기 구현
7. 물리 스위치를 이용한 E-stop CAN 프레임 생성
8. CAN 우선순위에 따른 E-stop 지연 및 starvation 비교
9. 송신 성공, 폐기, 지연 및 버스 상태 기록

Gazebo 물리 모델 자체와 어뢰 제어 로직을 임베디드 보드로 이식하는 작업은
현재 범위에 포함하지 않는다.

## 4. 하드웨어 구성

### 4.1 장치

| 장치 | 역할 |
| --- | --- |
| Ubuntu PC | Gazebo/SITL, ROS 2, UART 송수신 및 결과 기록 |
| ESP32-S3 A | PC UART와 CAN 사이의 양방향 게이트웨이 |
| ESP32-S3 B | BlueROV 회피·제어 로직 실행 |
| Teensy 4.1 | 가상 소나 덤프 생성 및 E-stop 스위치 감지 |
| SN65HVD230 | 각 CAN 컨트롤러를 CANH/CANL 물리 계층에 연결 |
| E-stop 스위치 | 우선순위 시험용 긴급정지 입력 |
| 120 Ω 종단저항 2개 | CAN 버스 양 끝 종단 |

ESP32 A와 ESP32 B는 각각 SN65HVD230 하나를 사용한다. Teensy에서는 덤프와
E-stop을 서로 독립적으로 중재시키기 위해 CAN 컨트롤러 2개와 SN65HVD230
2개를 사용하는 구성을 기준으로 한다.

```text
ESP32 A CAN ─ SN65HVD230 ─┐
ESP32 B CAN ─ SN65HVD230 ─┼─ CANH / CANL / GND 공통 버스
Teensy CAN1 ─ SN65HVD230 ─┤  (가상 소나 덤프)
Teensy CAN2 ─ SN65HVD230 ─┘  (E-stop)
```

Teensy 4.1은 CAN 컨트롤러 3개를 제공하며, 이번 구성에서는 그중 2개를
사용한다. 각 CAN 컨트롤러에는 별도 CAN 트랜시버가 필요하다.

### 4.2 CAN 배선 원칙

- 모든 노드의 CANH, CANL 및 GND를 공통으로 연결한다.
- 120 Ω 종단저항은 버스의 물리적 양 끝에만 배치한다.
- 각 노드의 분기선은 가능한 짧게 유지한다.
- ESP32 또는 Teensy의 CAN TX/RX 핀을 CANH/CANL에 직접 연결하지 않는다.
- 모든 노드의 bitrate와 CAN 프레임 형식을 동일하게 설정한다.

### 4.3 현재 기준 통신 설정

| 항목 | 기준값 |
| --- | --- |
| PC-ESP32 UART 장치 | `/dev/ttyACM0` |
| UART 설정 | 115200, 8N1, 흐름 제어 없음 |
| CAN 종류 | Classical CAN |
| CAN bitrate | 250 kbit/s |
| CAN ID 형식 | 표준 11-bit ID |
| CAN payload 최대 크기 | 프레임당 8 byte |

UART 패킷 구조와 실제 HIL 데이터별 CAN ID는 데이터 목록을 확정한 뒤 별도
표로 정의한다.

## 5. 노드별 소프트웨어 역할

### 5.1 PC: Gazebo/SITL 및 ROS 2

PC 측 ROS 2 노드는 BlueROV 회피와 제어에 필요한 토픽을 구독한다. 구독한
메시지를 임베디드 통신용 패킷으로 직렬화하여 ESP32 A에 UART로 전송한다.

ESP32 B가 계산한 6개 추진기 출력을 역방향으로 수신하면 SITL의 추진기 명령
토픽으로 발행한다.

현재 프로젝트를 기준으로 검토할 입력 데이터는 다음과 같다.

- BlueROV 위치 `(x, y, z)`
- BlueROV 선속도 및 각속도
- BlueROV 자세
- IMU
- 압력 및 깊이
- DVL 속도
- 위협 어뢰 odometry
- 임무 목표 위치
- 회피·경로 계획·제어에 추가로 필요한 상태

경로 자체를 PC에서 생성할지 ESP32 B에서 생성할지는 제어 로직 이식 범위를
확정하면서 결정한다. 최종 입력 목록, 갱신 주기, 단위 및 좌표계는 UART/CAN
패킷 명세를 작성할 때 확정한다.

### 5.2 ESP32 A: UART-CAN 게이트웨이

ESP32 A는 데이터 내용을 계산하지 않고 통신 경로를 연결한다.

```text
PC UART 수신 → 패킷 검증 → CAN 프레임 분할 및 송신
CAN 제어 출력 수신 → 패킷 조립 및 검증 → PC UART 송신
```

필요한 기능은 다음과 같다.

- UART 패킷 헤더, 길이, 메시지 종류 및 checksum 검사
- 큰 ROS 데이터의 CAN 8-byte 프레임 분할
- 순서 번호를 이용한 누락 및 순서 오류 검출
- CAN 프레임 재조립
- timeout 시 오래된 데이터 폐기
- 통신 오류 및 폐기 카운터 제공

### 5.3 ESP32 B: BlueROV 제어기

ESP32 B는 CAN으로 받은 최신 상태를 이용해 BlueROV 회피와 제어 로직을
실행한다.

예상 처리 단계는 다음과 같다.

```text
CAN 상태 수신
  → 상태 유효성 및 timeout 검사
  → 회피/경로 처리
  → 제어 로직 실행
  → 6개 추진기 명령 계산
  → CAN 송신
```

필수 안전 동작은 다음과 같다.

- E-stop 수신 즉시 추진기 명령을 0 또는 정의된 안전값으로 변경
- 필수 상태 데이터 timeout 시 안전 출력 적용
- NaN, 범위 초과 및 손상된 패킷 거부
- 제어 주기와 계산시간 기록
- E-stop 수신시각과 안전 출력 적용시각 기록

### 5.4 Teensy 4.1: 부하 생성기 및 E-stop 송신기

Teensy는 두 가지 독립 역할을 수행한다.

#### CAN1: 가상 소나 덤프

- 8-byte Classical CAN 프레임을 고속으로 생성한다.
- CAN 버스의 요청 부하가 약 100% 이상이 되도록 송신률을 설정한다.
- 소나 데이터는 실시간 최신성이 중요하다고 가정한다.
- 전송하지 못한 오래된 데이터는 재전송을 위해 누적하지 않는다.
- 큐 깊이를 작게 유지하고 새 데이터가 들어오면 오래된 데이터를 폐기한다.
- 생성 수, 전송 성공 수 및 폐기 수를 기록한다.

#### CAN2: E-stop

- 물리 스위치 상태를 읽는다.
- 디바운싱 후 E-stop CAN 프레임을 즉시 송신한다.
- 스위치 감지시각과 CAN 송신 요청시각을 기록한다.
- 시험 모드에 따라 E-stop CAN ID의 우선순위를 변경한다.

덤프와 E-stop이 별도 CAN 컨트롤러를 사용하므로 Teensy 내부 단일 FIFO의
순서보다 실제 CAN 버스의 ID 중재 결과를 더 명확하게 관찰할 수 있다.

## 6. HIL 데이터 설계 원칙

### 6.1 데이터 우선순위

실제 운용 기준 우선순위는 다음 순서를 기본으로 한다.

```text
1. E-stop 및 안전 상태
2. 제어에 직접 필요한 빠른 상태 데이터
3. 추진기 제어 출력
4. 목표 및 저주기 설정 데이터
5. 로그 및 가상 소나 덤프
```

표준 CAN에서는 CAN ID 숫자가 작을수록 우선순위가 높다. 최종 ID를 정할 때
기능별 대역을 나누고 동일 ID를 서로 다른 송신 노드가 동시에 사용하지 않도록
한다.

### 6.2 최신 데이터 유지

제어 상태와 소나 데이터는 오래된 데이터가 뒤늦게 전송되지 않도록 최신값
중심으로 처리한다. 특히 가상 소나 덤프는 다음 정책을 사용한다.

```text
새 소나 프레임 생성
  ├─ 즉시 전송 가능: 전송
  └─ 전송 불가능: 오래된 대기 데이터를 폐기하고 최신값만 유지
```

E-stop은 일반 덤프와 같은 폐기 정책을 사용하지 않는다. E-stop의 반복 횟수와
확인 방식은 안전 프로토콜을 설계하면서 확정한다.

### 6.3 단위와 좌표계

ROS 2 메시지를 임베디드 데이터로 변환할 때 다음 항목을 명시해야 한다.

- 각 필드의 단위
- `map`, `odom`, `base_link` 등 좌표계
- 정수 고정소수점 또는 IEEE 754 부동소수점 사용 여부
- byte order: big-endian으로 통일, DBC 표기는 Motorola
- 범위와 해상도
- 생성시각, 순서 번호 및 timeout

상세 CAN ID, payload, 통신 매트릭스와 상위 프로토콜 설명은
[`CAN_PROTOCOL_GUIDE.md`](CAN_PROTOCOL_GUIDE.md)를 따른다.


## 7. CAN 포화 및 E-stop 우선순위 실험

### 7.1 목적

가상 소나 덤프로 CAN 버스를 거의 100% 점유시키고, E-stop 우선순위에 따른
전송 지연과 starvation 가능성을 비교한다.

### 7.2 부하 생성 방식

250 kbit/s Classical CAN에서 표준 ID와 8-byte payload를 사용하는 프레임은
데이터 패턴에 따른 bit stuffing을 포함해 대략 444~540 μs 동안 버스를
점유한다. 초기 부하 시험에서는 Teensy CAN1이 약 400 μs 이하의 요청 주기로
프레임을 생성하여 물리 버스 처리량보다 많은 데이터를 공급한다.

이는 모든 데이터를 전달하기 위한 설정이 아니다. CAN 버스를 포화 상태로
유지하고, 처리하지 못한 소나 데이터가 최신값 유지 정책에 따라 폐기되는지를
확인하기 위한 설정이다.

실제 버스 점유율은 CAN 분석기 또는 수신 timestamp를 이용해 측정하며 계산값만
으로 100%라고 단정하지 않는다.

### 7.3 시험 모드

최종 CAN ID 값은 구현 시 확정하되 다음 상대적 우선순위를 사용한다.

#### 시험 A: 정상 우선순위

```text
E-stop: 최고 우선순위
제어 및 상태: 중간 우선순위
가상 소나 덤프: 최저 우선순위
```

예상 결과는 현재 전송 중인 CAN 프레임 하나가 끝난 후 E-stop이 다음 중재에서
승리하는 것이다.

#### 시험 B: 역전 우선순위

```text
가상 소나 덤프: 최고 우선순위
제어 및 상태: 중간 우선순위
E-stop: 최저 우선순위
```

덤프 프레임이 항상 송신 대기 중이면 E-stop이 반복해서 중재에서 패배하여 큰
지연 또는 starvation이 발생할 수 있다. 이 시험은 CAN 우선순위의 영향을
관찰하기 위한 의도적인 비정상 구성이다.

### 7.4 측정 항목

- CAN 버스 점유율
- E-stop 스위치 감지시각
- E-stop 송신 요청시각
- ESP32 B의 E-stop 수신시각
- ESP32 B의 안전 출력 적용시각
- SITL에 안전 추진기 출력이 반영된 시각
- E-stop end-to-end 지연
- 소나 프레임 생성, 송신 성공 및 폐기 수
- 상태 및 제어 프레임 지연과 누락 수
- CAN error 및 bus-off 발생 횟수

가능하면 스위치 입력과 CAN 신호를 로직 분석기 또는 오실로스코프로 동시에
관찰한다. 장비가 없으면 각 노드의 고해상도 timestamp와 시험 순서 번호를
사용한다.

### 7.5 안전 조건

- 역전 우선순위 시험은 실제 추진기나 위험한 구동부와 분리하여 수행한다.
- 시험용 CAN E-stop을 실제 하드웨어 전원 차단 장치의 대체물로 사용하지 않는다.
- 통신이 끊기거나 필수 데이터가 timeout되면 ESP32 B는 안전 출력을 적용한다.
- 포화 시험 전 정상 우선순위에서 E-stop 동작을 먼저 검증한다.

## 8. 현재 구현 상태

현재 `esp32_bridge`에는 다음 기능이 구현되어 있다.

### PC ROS 2 C++ 노드

- 키보드 입력을 Enter 없이 1 byte씩 수신
- `/dev/ttyACM0`, 115200, 8N1로 ESP32에 원본 byte 전송
- UART 장치와 baud rate를 ROS 파라미터로 변경 가능
- `Ctrl+C` 종료 및 터미널 설정 복구

### ESP32-S3 송신 펌웨어

- USB Serial/JTAG에서 1 byte 수신
- CAN ID `0x200`, DLC 1 프레임으로 변환
- GPIO17/GPIO18과 SN65HVD230을 이용해 500 kbit/s CAN 송신

### ESP32-S3 수신 모니터

- 500 kbit/s CAN 프레임 수신
- CAN ID, DLC, hexadecimal payload 및 ASCII 출력
- 수신 큐 포화 시 프레임 폐기 로그 출력

현재 코드는 UART-CAN 기본 연결을 검증하기 위한 단계이며, 아직 실제 SITL
메시지 직렬화, 양방향 게이트웨이, 제어 로직 이식, Teensy 부하 생성 및 E-stop
시험은 구현되지 않았다.

## 9. 단계별 구현 계획

### 단계 1: 하드웨어 통신 검증

- ESP32 A/B 및 Teensy에 SN65HVD230 연결
- CANH/CANL/GND와 종단저항 확인
- 모든 노드에서 250 kbit/s 송수신 확인
- 고정 counter 프레임의 누락과 오류 확인

완료 조건: 세 장치가 동일 CAN 버스에서 정상적으로 송수신하고 ACK 오류가 없다.

### 단계 2: HIL 데이터 명세 작성

- SITL에서 보낼 ROS 토픽과 필드 확정
- 보드에서 반환할 6개 추진기 출력 형식 확정
- UART 패킷 및 CAN ID 표 작성
- 분할, 재조립, 순서 번호, checksum 및 timeout 정의

완료 조건: 모든 데이터가 송신자, 수신자, 주기, 크기, 우선순위와 함께 표로
정의되어 있다.

### 단계 3: ESP32 A 양방향 게이트웨이

- UART→CAN 상태 데이터 전달
- CAN→UART 추진기 출력 전달
- 오류 검출, timeout 및 통계 구현

완료 조건: PC에서 보낸 시험 상태가 ESP32 B에 도착하고, 시험 출력이 PC로
동일하게 반환된다.

### 단계 4: ESP32 B 제어 로직 이식

- 입력 상태 저장 및 유효성 검사
- 회피·경로·제어 로직 단계별 이식
- 6개 추진기 출력 생성
- E-stop 및 데이터 timeout 안전 처리

완료 조건: 동일 입력에서 기존 SITL 제어 로직과 허용 오차 내의 출력을 만든다.

### 단계 5: SITL 폐루프 연결

- ROS 2 토픽을 UART 패킷으로 변환
- ESP32 B 출력을 SITL 추진기에 적용
- 제어 주기, UART/CAN 지연 및 안정성 확인

완료 조건: BlueROV가 보드에서 계산된 출력으로 Gazebo 안에서 폐루프 제어된다.

### 단계 6: Teensy 소나 부하 및 E-stop 구현

- CAN1 최신값 기반 덤프 생성기
- CAN2 물리 E-stop 송신기
- 정상/역전 우선순위 모드
- 송신, 폐기 및 timestamp 통계

완료 조건: CAN 버스를 의도한 부하까지 올리고 두 우선순위 모드에서 E-stop을
반복 측정할 수 있다.

### 단계 7: 결과 분석

- 부하율별 E-stop 최소·평균·최대 지연 비교
- 정상/역전 우선순위 결과 비교
- 소나 폐기율과 제어 데이터 지연 분석
- CAN ID 및 송신률 설계 기준 정리
