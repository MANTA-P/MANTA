## 1. 저장소 코드 변경 (커밋 `99a1089`)

(이후 dev 머지로 `610401b`로도 히스토리에 들어감)

### 1-1. A*/DVO/hybrid 3-way 분리

같은 BlueROV·같은 목적지에서 A* 단독과 DVO 단독을 각각 돌려 비교하기 위해 분리했다.

| 모드 | 전역 계획 | 국소 회피 | 계획 주기 |
|---|---|---|---|
| `astar` | A*(예측 통로) | 없음 | 충돌·이탈 시에만 |
| `dvo` | 없음 | DVO 단독, 미션 목표 직행 | 매 틱 5Hz |
| `hybrid` | A* | DVO 국소 우회 | A*는 필요시 / DVO 매 틱 |

**DVO 모드는 A*를 전혀 호출하지 않는다** — `runPlanner()`에서 조기 반환하고
예측 통로도 만들지 않는다.

### 1-2. 공통 인터페이스

A*든 DVO든 출력이 같으므로(`std::vector<Point3D>` → `/uuv/reference_path`),
알고리즘 분기는 `runPlanner()` 한 곳에만 두고 발행은 `publishPlan()`이 맡는다.

```
runPlanner()  ← 알고리즘 분기가 있는 유일한 곳
   ↓ PlanResult (알고리즘 무관 공통 타입)
publishPlan() ← 무슨 플래너였는지 모름
   ↓ /uuv/reference_path → DataHub → PathFollower → PPID
```

### 1-3. 런타임 전환

시뮬을 끄지 않고 알고리즘을 바꾼다:
```bash
ros2 param set /bluerov_integration_node planning.planner dvo
```
플래너를 config가 아니라 **입력**(`PlanningInput`/`PlanRequest`)으로 다뤄, 계산 도중
전환돼도 그 요청은 일관되게 끝난다. 전환 시 경로 캐시를 비워 즉시 재계획한다.

### 1-4. DVO 독립 실행

기존 DVO는 A*에 종속돼 있었다 — 충돌 위험이 없으면 빈 경로를 반환했고,
`local_goal` 도달해야만 성공으로 쳤다(100 m 목표는 한 번에 불가).
→ `DynamicVOOptions::standalone` 플래그로 (a) 위험이 없어도 목표까지 롤아웃
(b) 부분 경로도 성공 인정. 기본값 false라 **하이브리드 동작은 불변**.

### 1-5. RViz 렉 수정

어뢰를 만나면 RViz가 급격히 느려졌다. DVO 병합으로 `execute()`가 매 틱 돌게 되면서
예측 박스 33개를 개별 마커로 5Hz 발행 → **165 msg/s**.
→ **CUBE_LIST 1개**로 묶어 5 msg/s(약 97% 감소). 화면은 동일. QoS depth 20→64.

### 1-6. 파일 분리 3건

| 대상 | 이동 | 이유 |
|---|---|---|
| 파라미터 로딩 | → `planning_params.cpp` (신규 149줄) | 파라미터 기본값만 바꿀 때 이 파일만 재컴파일 |
| `selectLocalTarget`/`mergePaths` | → `planning_core` | ROS 참조 0인데 ROS 파일에 있었음 |
| `runPlanner`의 로그 5개 | → `PlanFailure` 코드 | **`runPlanner`의 ROS 의존 5→0** |

결과: `planning_module.cpp` 707 → 552줄. `runPlanner()` 112줄이 통째로 순수해져
ESP32 이식 범위가 늘었다.

  (PathFollower가 경로 끝을 "미션 목표 도달"로 오판해 회피를 무시하는 것 방지)

### 2-1. 다방향 시나리오

`manta2`가 `yaw`를 안 넘겨서 어뢰가 항상 +Y로만 발사됐다.
`ros2 launch`를 직접 호출해 방향을 지정한다
(`yaw = atan2(-(목표x-어뢰x), 목표y-어뢰y)`).

| 시나리오 | 어뢰 스폰 | yaw | 의도 |
|---|---|---|---|
| `front` | (0, −150) | 0 | 정면충돌, 접근 15 m/s |
| `rear` | (0, +60) | π | **후방추격 — A*가 반응 못 할 수 있는 조건** |
| `side` | (−80, −50) | −π/2 | 측면횡단 |
| `diag` | (−70, −120) | −0.95 | 대각접근 |

### 2-2. pty 자동 발사

어뢰 제어가 `/dev/tty`에서 키를 읽으므로, `pexpect`로 가상 터미널에 띄워
모드 선택과 발사를 프로그램으로 넣는다. 사람 손 없이 유도 모드(2/3)까지 자동화된다.

### 2-3. 어뢰 속도 3단계 (실측 기반)

`speed_probe.py`로 직접 측정한 값이다(모드1 직진 기준):

| `r` 횟수 | 추력 | 속도 |
|---|---|---|
| 3 | 300 | 6.53 m/s (12.7 kt) |
| 5 | 500 | 8.51 m/s (16.5 kt) |
| 7 | 700 | 10.15 m/s (19.7 kt) |
| **10** | **1000** | **12.19 m/s (23.7 kt)** ← 상한 |
| 12 | 1000 | 12.23 m/s (변화 없음) |

→ 단계: `slow`(3회, 6.5 m/s) / `mid`(5회, 8.5 m/s) / `fast`(10회, 12.2 m/s)

**한계**: `glider_slocum`은 최대 23.7 kt가 천장이라 실제 어뢰의 공격 속도
(40~50 kt)는 재현되지 않는다. 탐색~고속순항 구간만 다룬다.

### 2-4. 결과 자동 기록

### 자동 실험 (사람 손 없이)

```bash
cd ~/manta_experiments

# 한 판: 시나리오 / 플래너 / 어뢰모드 / 속도
./auto_run.py rear astar 3 --speed fast

# 전체 조합 48회 (4 시나리오 x 2 플래너 x 2 모드 x 3 속도), 약 100분

# 결과를 표로
./auto_run.py --summary
```

인자 설명:

| 인자 | 값 | 뜻 |
|---|---|---|
| 시나리오 | `front` `rear` `side` `diag` | 어뢰가 오는 방향 |

| `--watch` | 초 (기본 45) | 발사 후 결과 관찰 시간 |
| `--no-gazebo` | — | Gazebo가 이미 떠 있으면 재사용 (빠름) |

Gazebo는 headless로 뜨므로 화면을 가리지 않는다. 실험 로그는 `results/`에 쌓인다.

## 3. 실험 과정에서 잡은 문제들

### 3-1. 1차 배치 16회 전부 무효 — 어뢰 재빌드 누락

16판 모두 `AVOIDED`가 나왔는데 최근접 거리가 9.3~10.5 m로 지나치게 일정했다.
어뢰 위치를 찍어보니 **z = −14.7 m까지 가라앉아 ROV(z = −1 m) 밑으로 지나가고 있었다.**
회피가 아니라 깊이 차이로 빗나간 것이다.

원인은 **어뢰 바이너리가 10일 묵은 것**이었다:

| | |
|---|---|
| 바이너리 빌드 | 8/10 19:32 |
| 소스 수정 | 8/20 23:34 |
| 바이너리에 `PngController`/`SimpleTracking` 심볼 | **0개** |
| 바이너리에 옛 `MANUAL`/`AUTO_TRACK` 문자열 | 있음 |

옛 구조라 숫자키 처리가 아예 없었고, 핀 제어도 없어 부력대로 가라앉았다.
`colcon build --packages-select torpedo_control_v2`로 해결.

> **교훈**: 실험 전에 `manta_rebuild` 한 번. 30초면 되고, 안 하면 40분을 날린다.
> 스크립트에 빌드 최신성 자동 확인을 넣어 소스가 더 최신이면 실행을 거부하게 했다.

### 3-2. pty 버퍼에 쌓인 옛 화면

재빌드 후에도 배치에서 모드 전환이 실패했다. 진단 스크립트로는 되는데 배치에서만
안 됐다. 원인은 어뢰 CLI가 전체 화면을 계속 다시 그리는데, 발사 전 대기를
`time.sleep()`으로 하는 동안 출력이 버퍼에 쌓여 **6초 전 화면을 읽고 있었던 것**.

→ 대기 중에도 pty를 계속 읽어 버퍼를 비우고, 모드 전환은 확인될 때까지 재시도.
발사 후 관찰 구간에서도 계속 읽는다(버퍼가 차면 어뢰 노드가 출력에서 막혀 멈춘다).

### 3-3. 목표가 전달되지 않아 ROV가 정지

`manta4`(target)는 대화형이라 stdin 없이 띄우면 즉시 끝나고, `transient_local`로
발행한 목표가 퍼블리셔와 함께 사라진다. `path=0`, 계획 0회로 ROV가 제자리에 있는데
어뢰가 빗나가 `AVOIDED`로 찍혔다.

→ `ros2 topic pub -r 1`로 퍼블리셔를 살려두고 발행. 계획 0회면 `INVALID_NO_PLAN`으로
결과를 무효 처리해 가짜 성공이 표에 섞이지 않게 했다.

### 3-4. 발사 타이밍

준비 작업(목표 전달 확인 25초 + 센서 OK 45초 + 모드 전환 20초)이 전부 목표 발행
**뒤에** 있어서, 어뢰가 나갈 때쯤 ROV가 수십 미터 앞서 있었다.

→ 센서 확인·모드 전환을 목표 발행 **앞으로** 옮기고, 발사 지연은 2초로 줄였다.

## 4. 현재 유효한 관측

1차 배치는 무효지만 알고리즘 특성 자체는 측정됐다:

| | A* | DVO |
|---|---|---|
| 재계획 횟수 | **1회** | **90~109회** |
| 평균 계획시간 | 2.1~2.9 ms | 5.4~6.3 ms |
| 예측 통로 박스 | 최대 33개 | 0개(설계상 미사용) |

재빌드 후 단발 검증에서 **`rear`/`astar`/PNG → HIT (최근접 0.94 m)** 가 나왔다.
A*가 후방 어뢰에 계획 1회로 무반응했고, 처음 세우신 가설과 일치한다.

**아직 전체 배치는 돌리지 않았다** — 속도 3단계까지 반영해 재실행 예정.
조합은 4 시나리오 × 2 플래너 × 2 모드 × 3 속도 = **48회**(약 100분).

## 5. 참고: ESP32 이식 사전조사

| | A* | DVO |
|---|---|---|
| 메모리 | ~212 KB (격자 96KB + 탐색 116KB) | 수 KB |
| x86 시간 | 0.345 ms | 0.656 ms |

- ESP32 SRAM 520 KB(실사용 ~300 KB) → **DVO는 여유, A*는 미션 거리에 비례해 위험**
  (해상도 1 m로 100 m 미션이면 592 KB → 불가. 2 m면 86 KB → 가능)
- `Point3D`가 double×3인데 ESP32 FPU는 single-precision 전용 →
  **`double`→`float` 전환이 최대 성능 변수**. 단 시간 변수는 double 유지
  (유닉스 시각 1.7e9를 float에 담으면 해상도가 128초로 뭉개짐)
- 통신/알고리즘 분리는 이미 완료 — 통신 계층만 micro-ROS나 시리얼로 교체하면 된다
- 그 외 정리 대상: `throw`(ESP32는 `-fno-exceptions`), 코어의 `std::string frame_id`,
  A*의 동적 컨테이너 → 격자 인덱스 배열
