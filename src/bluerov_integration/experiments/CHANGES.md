# 변경 내역 정리

`feature/avoid` 브랜치에서 수정한 내용. 무엇을 왜 바꿨는지와 그 근거를 남긴다.

수정 범위는 `src/team_min/`, `include/bluerov_integration/team_min/`,
`experiments/` 로 한정했다. 팀원 코드(`team_byung`, `integration`,
`torpedo_control_v2`, `dave`)는 건드리지 않았다.

**신규 9개 / 수정 11개 파일, 약 740줄 추가.**

## 1. 예측 통로가 회피 후 갱신되지 않던 문제 (수정)

### 증상

한 번 회피하고 나면 어뢰는 계속 움직이는데 **RViz의 예측 박스가 그 자리에
얼어붙었다.**

### 원인

박스를 그리는 `publishScene()` 이 `publishPlan()` 안에서만 불렸다.
그런데 A\* 는 히스테리시스 정책상 **경로가 통로와 충돌할 때만** 재계획한다
(측정상 한 판에 1회). 회피 경로를 한 번 잡으면 더는 계획이 돌지 않으므로
그릴 기회 자체가 없었다. 마커 QoS 가 `transient_local` 이라 옛 박스가
지워지지도 않았다.

**회피에 성공할수록 더 빨리 멈추는 구조였다.**

### 수정

| 대상 | 내용 |
|---|---|
| `planning_types.hpp` | `Decision` 에 `torpedo_corridor` 추가 |
| `planning_core.cpp` | 충돌검사용으로 이미 만들던 통로를 그대로 실어 보냄 |
| `rviz_visualizer.*` | `publishTorpedoCorridor()` 분리, `publishScene()` 에서 통로 인자 제거 |
| `planning_module.cpp` | 상태 갱신 주기(5Hz)마다 발행 |

코어가 `needsReplan` 충돌검사용으로 **이미 매 틱 만들던** 통로를 재사용하므로
**계산량은 늘지 않는다.**

### 검증

시뮬 없이 코어에 합성 궤적을 먹여 확인:

- 600틱 중 **계획 요청 61틱 / 계획 없이 통로가 나온 539틱** — 예전엔 이
  539틱이 통째로 안 그려졌다
- AVOIDED 이후 521틱 **전부** 통로 생성

실제 시뮬에서 마커 좌표를 1초마다 기록해 재확인:

| 조건 | 통로 첫 박스와 어뢰 실제 위치의 어긋남 |
|---|---|
| 정면 접근 18초 | 최대 **0.20 m** |
| 후방 추격 45초 | 최대 **1.19 m** (박스 한 변 3 m) |

## 2. 시공간 A\* (신규)

`spacetime_astar.hpp` / `spacetime_astar.cpp` — **기존 `astar_planner` 는
그대로 두고 별도 파일로 추가**했다.

### 왜

기존 A\* 는 어뢰의 미래 궤적을 **정적 통로**(박스 19개)로 부풀려 막는다.
그래서 "어뢰가 지나간 뒤 그 자리를 통과한다"는 해가 원천 배제된다.

1989년 미 해군잠수함연맹 연구의 최적 혼합 전략은 **어뢰 방위를 가로지르기
54% / 멀어지기 46%** 인데, 과반인 가로지르기를 지금 구조가 표현할 수 없다.

### 무엇이 다른가

| | 기존 A\* | 시공간 A\* |
|---|---|---|
| 노드 | (x, y, z) | (x, y, z, **t**) |
| 점유 판정 | 시간 무관 | **그 시각에 비었나** |
| 이웃 | 26방향 | 26방향 + **대기**, 전부 t+1 |
| 비용 | 이동 거리 | 이동 **시간** |
| 속도 | 없음 | 연속 waypoint의 Δ위치/Δt |

### 성능 (오프라인 벤치마크)

| 설정 | 분기수 | 확장노드 | 시간 | 메모리 |
|---|---|---|---|---|
| 기존 A\* (임무 전체) | 26 | — | 0.74 ms | — |
| **시공간 1.0 m / 1.0 s** | 123 | **8** | **0.13 ms** | 72 KB |
| 시공간 0.75 m / 0.5 s | 33 | 15 | 0.09 ms | 37 KB |

**기존보다 5~8배 빠르다.** 임무 전체(288~990 m)가 아니라 어뢰 근처 8초만
풀기 때문이다.

### 안전장치 (벤치마크에서 찾은 함정)

**분기비율 검사**가 핵심이다.

$$\frac{v_{max} \cdot \Delta t}{\text{해상도}} \ge 2$$

이 값이 1이면 대각선 변위(1.41 × 해상도)가 한 스텝 상한을 넘어 잘려나가고
**축 이동만 남는다.** 그러면 우회가 극도로 비싸져 목표에 못 닿고 A\* 가 창
전체를 뒤진다 — 측정상 **172 ms / 9.7 MB**. 생성자에서 예외를 던져 막았다.

그 외:

- **도달 가능성 선검사** — lookahead 가 시간창 밖이면 탐색 전에 포기
- **대기 비용** — 제자리도 `dt` 만큼 비용이 들어 불필요하게 멈추지 않음

## 3. TTC 기반 교전 국면 전환 (신규)

`planning_types.hpp` 의 `EngagementPhase`, `TtcSwitchConfig` +
`planning_core.cpp` 의 상태기계.

### 왜

실측에서 드러난 것:

| 측정 | 값 | 의미 |
|---|---|---|
| A\* 회피 시작 | 150 m 지점부터 | PN 이 상쇄할 시간이 충분 |
| A\* 우회량 | **정확히 2.00 m** | 최단경로 = 최소 여유 |
| PPID 횡방향 명령 | 급변 없음 | 급기동을 한 적이 없음 |
| 피격 최근접 | 0.55~0.99 m | 피격반경 1.0 m **바로 아래** |

**A\* 는 일찍 완만하게 2 m 비켜 가고, PN 어뢰는 그걸 리드각으로 상쇄한다.**
문헌이 말하는 PN 회피는 정반대 — **늦게, 급격하게**다.

### 3단계

```
TTC > 6초        [cruise]    A* 단독. DVO 안 씀
2~6초            [approach]  A* 경로를 DVO가 평상시 가중치로 다듬음
TTC < 1.85초     [break]     A* 무시. DVO가 이격 최대화만
어뢰 이탈 + 1.5초 [cruise 복귀] 현재 위치에서 A* 재계획
```

### 임계값 근거

**추정치를 쓰지 않았다.** 저장소 코드에서 읽은 값과 문헌 인용만 썼다.

| 값 | 근거 |
|---|---|
| `break_sec` = **1.85** | Zarchan *Tactical and Strategic Missile Guidance*: PN 회피는 $t_{go} \approx 3{\sim}5\,\tau_g$ 에서 이격 최대, N'=3 이면 4$\tau_g$ |
| `approach_sec` = **6.0** | DVO 자신의 `prediction_horizon = 6.0`. 그보다 일찍 켜도 충돌원뿔이 어뢰를 못 봄 |
| `dwell_sec` = **1.5** | [arXiv 2506.20311](https://arxiv.org/html/2506.20311v1) C2 조건의 $K \approx 1.5$초 |

$\tau_g$ 는 전부 이 저장소에서 읽은 값으로 계산했다:

```
model.sdf                     Izz = 13.193856,  nR = 32   → Izz/nR = 0.412초
default_control_config.cpp    update_rate_hz = 20         → 0.050초
                              png_navigation_constant = 3.0 → N' = 3

τ_g = 0.412 + 0.050 = 0.46초    4τ_g = 1.85초
```

시뮬 어뢰는 정확한 odometry 를 받아 탐색기 필터가 없다. 실제 음향호밍
어뢰는 필터 지연이 붙어 $\tau_g$ 가 더 크므로, **1.85초는 실제보다 이른 쪽
(= 회피에 불리한 보수적 값)** 이다.

### 진동 방지

위험한 국면으로는 **즉시** 올라가고(늦으면 못 피한다), 안전한 쪽으로
내려갈 때만 체류시간을 지킨다. 실측에서 정적 A\* 가 재계획마다 회피 축을
수직↔수평으로 바꾸는 걸(60~28 m 수직, 20~14 m 수평, 10 m 다시 수직)
확인해 넣었다.

## 4. DVO 비용함수 전환 (수정)

`dynamic_vo_planner.hpp` 의 `DynamicVOWeights`.

### 문제

가중치가 `.cpp` 에 상수로 박혀 있었고 **목표 항이 회피 항의 3배**였다:

$$\text{score} = 3.0 \cdot d_{목표} + 0.35 \cdot \|v - v_{선호}\| + 1.0 \cdot \frac{1}{여유}$$

그래서 어뢰가 30 m 밖에 있든 3 m 앞에 있든 **"목표를 향하되 겨우 안
부딪히게"** 를 골랐다. A\* 가 2.0 m 만 비키는 것과 같은 성질의 문제다.

`0.5 × \|v - v_{이전}\|` 항은 **속도 급변에 벌점**이라 급기동을 직접 막는다.

### 수정

상수를 옵션으로 빼고 국면별 2세트로 나눴다:

| | 목표 | 목표지향 | 연속성 | 이격 |
|---|---|---|---|---|
| 평상시 | 3.00 | 0.35 | 0.175 | 1.0 |
| **급기동** | **0.10** | **0.00** | 0.30 | **10.0** |

평상시 값은 **기존 상수와 동일**해 동작이 안 바뀐다.

`continuity` 를 0 으로 두지 않은 이유: 방향이 정해진 뒤엔 유지해야 한다.
전환 직후엔 `clearance`(가중치 10, 이격 1 m면 비용 10)가
`continuity`(0.3 × 6 m/s = 1.8)를 압도해 급변 자체는 막히지 않는다.

## 5. 속도 출력 계층 (신규, 미연결)

`velocity_command.*`, `velocity_pid.*` — **컴파일만 되고 파이프라인에는
안 붙어 있다.**

### 왜 만들었나

`PathFollower` 코드를 읽어 확인한 것:

```
경로에서 가장 가까운 waypoint → waypoint_reached_radius(0.75 m) 안이면 전진
→ lookahead_distance(2.0 m) 만큼 더 가서 목표점 선택
→ PositionP: v = clamp(1.5 × 거리, 3.0)
```

목표점이 **항상 약 2.0 m 앞**이라 $v = 1.5 \times 2.0 = 3.0$ — **언제나
최대속도**다. DVO 가 "1 m/s 로 천천히" 를 결정해도 그 정보가 사라진다.

VO 이론에서 감속은 핵심 회피 수단인데 **지금 구조로는 표현할 수 없다.**

### 왜 안 붙였나

붙이려면 `team_byung/ppid_controller` 수정이 필요하다(팀 코드). 그리고
오늘 측정에서 **제어는 병목이 아님**이 확인됐다:

- 속도 추종 오차 **0.01 m/s**
- 실제 도달 최대속력 **3.09 m/s** (설정 상한 3.0)
- 추력 포화 16.8% (주로 초기 가속)

감속은 PN 어뢰에 오히려 불리하다 — 느려지면 예측이 쉬워진다. 문헌이 말하는
PN 회피는 속도 변화가 아니라 **횡가속**이고, 그건 PPID 가 이미 최대로 낸다.

### 내용

- `velocity_command` — 시공간 경로/DVO 결과에서 속도 추출 + **경로 이탈 보정**
  (PositionP 를 우회하면 위치 피드백이 사라지므로 DWA 의 경로거리 항,
  LOS 의 cross-track 과 같은 발상으로 흡수)
- `velocity_pid` — 속도 PID 단독(위치 P 루프 없음). ROS·STL 컨테이너·동적
  할당 없이 작성해 ESP32 이식 대상

`team_byung` PPID 와 필드 의미를 맞췄다. 처음에 잘못 읽어 고친 부분:

- `PIDGains{60, 0.5, 1.0, 2.0, 450}` = {kp, ki, kd, **integral_limit=2.0**,
  **output_limit=450**} — 뒤 두 개를 반대로 넣었었다
- 피드포워드가 선형이 아니라 **2차**: `gain × target × |target|`
  (항력이 $v^2$ 이므로 정속 유지 추력도 $v^2$)

## 6. 실험 도구 (`experiments/`)

### 축척 도입 — `torpedo_scaling.py` (신규)

시뮬 값을 손으로 고르면 "왜 그 값이냐"에 답할 수 없어, **앵커 하나에서
전부 유도**한다.

> **잠수함 순항 20 kt ↔ 우리 ROV 3.0 m/s**

| 척도 | 정의 | 값 |
|---|---|---|
| 속도 σ | `3.0 / (20 × 0.5144)` | 0.2916 |
| 시간 τ | 실험시간 제약에서 선택 | 0.30 |
| 거리 λ | `σ × τ` | 0.0875 (1:11.4) |

이 앵커 하나로 실제 무장이 5% 이내로 떨어진다:

| 어뢰 | 실제 | 시뮬 속도 | 오차 | `r` 횟수 |
|---|---|---|---|---|
| 백상어 K731 | 35 kt / 30 km | 5.35 m/s | +1.9% | 2 |
| 청상어 K745 | 45 kt / 9 km | 6.62 m/s | −1.9% | 3 |
| Mk 48 ADCAP | 55 kt / 50 km | 8.64 m/s | +4.7% | 5 |

추력이 100 단위로만 올라가는데도 5% 안에 드는 건, `model.sdf` 항력계수에서
추력→속도 관계를 닫힌형으로 유도했기 때문이다:

$$2c = 8v + 12.474\,v^2$$

speed_probe 실측 4점과 **전부 1.5% 이내** 일치.

속도 설정 3단계는 $R \propto 1/v^2$ (연료 고정, 항력 $v^2$)를 쓴다.
Mk 48 공개 제원 "40 kt에서 38마일"을 55 kt로 환산하면 20.1마일로 공표치
21마일과 맞는다.

### 발사거리를 방향별로 유도

접근속도가 정면 8.4 m/s, 후방 1.4 m/s 로 6배 차이나서 거리를 같게 두면
**후방은 판정시간 안에 붙지도 못한다** (실측: rear/백상어 교전 0회).

거리를 고정하는 대신 **"발사 후 약 20초에 교전 시작"** 을 방향마다 맞춘다.

| 어뢰 | front | diag | side | rear |
|---|---|---|---|---|
| 백상어 | 197 m | 179 m | 137 m | **77 m** |
| 청상어 | 222 m | 205 m | 162 m | **102 m** |
| Mk 48 | 263 m | 245 m | 203 m | **143 m** |

### 임무거리를 판정시간에서 역산

짧으면 ROV 가 목표에 먼저 도착해 멈추고, 남은 시간 동안 어뢰가 **정지표적**
을 때린다 — 회피 성능이 아니라 도착 시간을 재게 된다.

$$\text{임무거리} = v_{ROV} \times (\text{판정시간} + \text{타력 10초}) \times 1.2$$

조건이 깨지면 실행을 **시작하지 않고** `INVALID_GOAL_TOO_NEAR` 로 중단한다.

### 연료 소진 재현

시뮬레이터에 연료 모델이 없어 어뢰가 무한히 달린다. 축척에서 계산한
운행시간이 지나면 **스페이스(`ThrottleStop`)** 를 pty 로 넣어 추력을 끊는다.
어뢰 코드는 그대로 두고 키 입력만 흉내낸다.

추력이 끊긴 어뢰는 항력으로 급감속한다 — 5초에 0.73 m/s, 10초에 0.29 m/s.

### 결과 저장·판별

| 기능 | 내용 |
|---|---|
| `results.csv` | 판마다 즉시 append. 중간에 멈춰도 남음 |
| `--report` | 표 + 회피 성공률 통계를 한 화면에 |
| `--coverage` | 48조합 중 무엇을 했고 무엇이 남았는지 |
| 48조합 고유번호 | 실행 순서와 무관한 고정 번호 |

무효 판별을 넣었다. 특히 **`INVALID_INTERRUPTED`** — 강제 종료로 어뢰
신호가 끊기면 코어가 "회피 성공"으로 마감하는데, 그걸 성공으로 세면
**가짜 데이터**가 섞인다. 실제로 한 판이 그렇게 기록됐던 걸 잡았다.

| 정상 회피가 무효 처리 | 교전 여부를 `[AVOIDED]` 개수로 판단. 어뢰가 교전반경 안에 계속 붙어 쫓으면 AVOIDED 가 안 찍힘 → `engagement started` 로 변경 |
| `--no-gazebo` 없다고 나옴 | README 에만 있고 **구현되지 않은 옵션**이었음. 삭제 |
| 첫 판이 항상 Gazebo 를 죽임 | "이 판이 띄웠나"와 "다음 판을 위해 남길까"가 한 인자로 묶여 있었음 |

### 실행 편의

| 파일 | 용도 |
|---|---|
| `run_experiment.sh` | 정리 → 빌드 → 보관 → 48판 → 보고를 **한 명령**으로 |
| `record_trajectories.sh` | 이미 도는 배치에 궤적 기록을 나중에 붙임 |
| `AGENT_PROMPT.md` | 다른 AI 에이전트에게 줄 프롬프트 |
| `--build` | 워크스페이스 루트를 알아서 찾아 빌드 |

`auto_run.py` 가 자기 폴더를 `sys.path` 에 넣어 **절대경로로 부르면 어느
디렉터리에서든** 동작한다.

## 7. 포기한 것

### Gazebo 재사용

판 사이에 Gazebo 를 유지해 판당 45초(전체 36분)를 아끼려 했으나 **포기**했다.

버그 두 개는 고쳤다:

- 월드명이 launch 인자(`dave_ocean_waves`)가 아니라 **`oceans_waves`**
- 과학적 표기(`6.26e-05`)의 지수 음수 부호를 정규식이 못 받음

세 번째가 근본적이었다 — **`set_pose` 가 위치만 옮기고 속도는 안 지운다.**
−3 m/s 로 달리던 ROV 를 원점에 놓아도 1초 뒤엔 −3 m 로 밀려나 검증을 통과
못 한다. 속도를 지우려면 월드 전체 리셋이 필요한데 ros_gz 브리지가 깨질
위험이 있다. 3시간에서 36분 아끼자고 감수할 위험이 아니다.

`--help` 에서 숨겼고 코드에 포기 이유를 남겼다.

### 시공간 A\* 의 회피 방향 관성

축이 흔들리는 걸 막으려 `previous_bias` 를 넣었는데 **효과가 없었다.**
축 진동은 **정적 A\* 의 문제**였고 시공간은 애초에 거의 직진한다(등속
예측을 신뢰하므로). 기능은 남겼지만(`bias_penalty`, 무해) 필요 없다.

## 8. 아직 확인하지 못한 것

- **어뢰 실제 선회반경** — `model.sdf` 1차근사는 1.4~2.7 m 인데 실제 어뢰는
  수십 m 다. 과대평가로 보이나 미검증. 이게 크면 급기동이 통하지 않는다
- **유도 시상수 실측** — `break_sec = 1.85` 의 근거를 실측으로 확인해야 함
- **시공간 A\* / 국면 전환의 실제 효과** — 오프라인 검증만 했고 시뮬 미검증
- ROV 의 z 가 목표(−1.0)보다 0.66 m 얕게 뜨는 현상 — 수직 회피인지
  PPID `heave_trim` 의 정상상태 오차인지 미확인

궤적 기록기를 붙여뒀으므로 앞 두 개는 이번 배치 데이터로 계산할 수 있다.
